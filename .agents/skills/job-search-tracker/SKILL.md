# Job Search Tracker

Use the project CLI (`src/cli.ts`) to inspect, search, and update job listings stored in `data/jobs.db`.

> **Important:** Invoke the CLI with `node --import tsx src/cli.ts ...` rather than `npm run dev -- ...`, because `npm` strips `--status`, `--limit`, and other `--flag` arguments before passing them to `tsx`.

## Workflows

### 1. Run Full ("run full" / "full job search")

Complete one agent-driven loop: search Java, C#, .NET, and Python across all configured sources, review only pending recent listings with the LLM, preserve valid assessments, and deliver the final HTML report:

```powershell
node --import tsx src/cli.ts full
```

- Use `--query "Python"` to run just one search. Other optional flags: `--limit 50` (per source and keyword), `--days 7`, `--sources <list>`, `--out <path>`, `--db <path>`. Carry the chosen `--days` and `--db` into the analysis export, and the chosen `--db` and final `--out` into the review import.
- Live scraping requires outbound network access (`BypassSandbox: true` if sandbox blocks network).
- Do not run `--help`, `package.json` checks, or ad-hoc SQLite/PowerShell queries.
- The `full` CLI command performs scraping and creates a preliminary report; it does not invoke a model. After scraping finishes, automatically complete workflow 6 (export pending jobs → LLM review of those jobs → validated database import → report). Do not reanalyze valid results, stop after scraping, or ask the user to request analysis separately.
- Continue the review of available database listings after source blocks or partial scrape failures, and disclose the incomplete source coverage. If LLM review or import fails, report that the full loop is incomplete.
- Verify the scrape outcome and successful review import with the updated count matching the pending export. Deliver the report generated by the import, which includes all recent records across all statuses without a row limit. Reply concisely with the scrape summary, `Jobs by source` counts (`new_count` + `latest_last_seen`), updated and preserved counts, and a clickable report link.

### 2. Check New Jobs ("what are the new jobs")

1. Check overall counts and recent scrape runs, and generate the timestamped HTML report (in parallel):
   ```powershell
   node --import tsx src/cli.ts stats
   node --import tsx src/cli.ts report --status new --days 7
   ```
   Optional report filters: `--source <id>`, `--search <text>`, `--limit 500`, `--out <path>`, `--db <path>`.
   (For raw JSON in scripts, use `node --import tsx src/cli.ts list --status new --limit 150 --json`; timestamp field is `last_seen_at`.)
2. Reply concisely with:
   - Total count by status, `Jobs by source` (`new_count` + `latest_last_seen`), and latest scrape run summary from `stats`.
   - A clickable `file:///` link to the generated HTML report (e.g. `data/reports/jobs-YYYY-MM-DD_HH-mm-ss.html`).
   - Offer to filter by keyword/salary/source or update statuses.

### 3. Run a Fresh Job Search

Search across configured sources and upsert results into `data/jobs.db`:

```powershell
node --import tsx src/cli.ts search --query "Java" --limit 50
```

- Optional: `--sources <comma-separated-ids>` (registered sources: `greenhouse`/`gh`, `lever`/`lv`, `mycareersfuture`/`mcf`, `jobstreet`/`js`).
- Live scraping makes outbound network requests and requires `BypassSandbox: true` if blocked by the sandbox.

### 4. Update Job Status & Notes

Valid statuses: `new`, `saved`, `applied`, `interviewing`, `rejected`, `archived`.

```powershell
node --import tsx src/cli.ts update --id 25 --status saved --notes "Strong match"
```

### 5. Discover ATS Boards

Probe Greenhouse/Lever boards for Singapore-active roles:

```powershell
node --import tsx src/cli.ts discover --tokens gh:company,lv:company
```

Or pass `--url <page-url>` and/or `--boards <path>`.

### 6. Analyze Project Domains & Update Probabilities

Use this workflow when asked to scan recent jobs, identify project types or probabilities, or update the database with LLM assessments. Default to the past 7 days unless the user specifies another window. When asked to analyze and update, complete both steps without another confirmation.

1. Export the pending scope:
   ```powershell
   node --import tsx src/cli.ts analyze --days 7 --out data/reports/llm-review-input.json
   ```
   This selects only missing or invalidated assessments across all statuses without a row limit, using posted dates with a last-seen fallback when unavailable. It exports `snapshotAt`, `days`, and pending `jobs`, each containing `id`, `input_hash`, `title`, `company`, and `description`. Exporting alone leaves the database unchanged and does not invoke an LLM. A valid assessment has method `llm`, a valid analysis timestamp, nonempty model, label and reasoning, exact source evidence, and a valid score. Completed `Unclear` results with null scores are valid; do not reassess them unless invalidated.
2. Read every exported listing and assess it individually with the acting LLM. Read in manageable batches if necessary, tracking IDs until all are covered. Use the stored title, employer, and description to infer the likely project domain and confidence. Do not replace this analysis with keyword matching, employer lookup tables, a fixed scoring formula, or default numeric scores. Scripts may assemble and validate decisions already made by the LLM; they must not generate the assessments.
3. Save the completed review to `data/reports/llm-project-review.json`:
   ```json
   {
     "model": "actual-reviewer-model",
     "snapshotAt": "copy the exported timestamp exactly",
     "days": 7,
     "decisions": [
       {
         "id": 123,
         "input_hash": "copy this job's exported hash exactly",
         "label": "Unclear",
         "score": null,
         "evidence": "exact quote from this stored listing",
         "reasoning": "Explain what the listing supports and why the domain is uncertain."
       }
     ]
   }
   ```
   Treat this as a schema example; replace every example value with the actual review. Preserve the exported `snapshotAt` and `days`. Record the actual reviewer model; do not invent a model identifier. Include every exported pending ID exactly once with its original hash, and never copy valid existing decisions into the import. If `jobs` is empty, skip listing analysis and use an empty `decisions` array with the acting agent's model and exported metadata to generate the final report without changing assessments.
   - Use a specific supported domain label and an integer `score` from 0 through 100. The score expresses subjective confidence in that named domain, not a calibrated probability or the candidate's hiring chances.
   - Use exactly `Unclear` with `score: null` when the available listing does not establish a domain. Only `Unclear` may have a null score.
   - Provide nonempty `evidence` quoting an exact contiguous substring from that job's title, company, or description, and nonempty `reasoning` explaining the judgment. For unclear jobs, quote the available generic text and explain the missing evidence.
   - Distinguish core banking, private banking, and wealth management. A banking technology role does not establish private banking; wealth management alone does not establish a private bank.
   - Do not infer a government-agency project merely from a government-linked employer. Keep public healthcare and education distinct where supported.
   - Treat recruiter listings and generic or missing descriptions as uncertain unless the stored text identifies the client or project domain.
4. Import the review and generate the report:
   ```powershell
   node --import tsx src/cli.ts analyze --input data/reports/llm-project-review.json
   ```
   Optional flags are `--db <path>` and `--out <html-path>`. During import, the review's `days` and `snapshotAt` determine scope; passing `--days` does not override them. The importer recomputes pending membership and rejects incomplete coverage, duplicate, already analyzed or out-of-scope IDs, changed hashes, invalid scores, and invalid evidence before committing any decisions in one transaction. If listings or pending membership changed, export again and reassess the current pending scope rather than replacing hashes or overwriting valid decisions.
5. Verify exit code `0`, the updated count matching the export count, and the generated report path. The report is built from rows read back after persistence. For an explicit database-verification request, a targeted read-only SQLite comparison is permitted: compare every reviewed ID's label, score, evidence, reasoning, method, model, and nonempty analysis timestamp against the review. Report mismatches instead of claiming success.

The importer writes `project_type`, `project_probability`, `project_evidence`, `project_reasoning`, `project_analysis_method` (`llm`), `project_analysis_model`, and `project_analyzed_at` only for pending records, preserving valid assessments, application status and notes. New listings and listings whose title, company, or description changes need another LLM review. Scraping does not assess them automatically; the HTML report displays pending results as `Not analyzed`. The final import report combines preserved and newly assessed recent records.

Reply with the number updated, concise domain counts including `Unclear`, and a clickable `file:///` link to the generated HTML report. Retain the input and review JSON files for audit.
